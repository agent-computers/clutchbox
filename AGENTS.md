# Coding instructions

- This is Clutchbox, under Apache-2.0. Every package must build, test, and run on its own, without any hosted service.
- Everything here is public, including history. Never commit credentials, captured cookies or profiles, customer data, or internal plans, and don't link to documents or issues outside this repository.
- Each package states what it is in its own README or the root table; keep it current when a package is added or changes status.
- Run `bun run format` before committing; `bun run lint`, `bun run typecheck`, and `bun run test` must pass. Fix a lint finding rather than suppressing it; when a rule is wrong for a line, use a `biome-ignore` comment that says why.
- Version the extension as `YY.MDD.PATCH`: `26.1016.0` is the first release on October 16, 2026 (January 1 is `101`), and PATCH counts up for later releases that day, restarting at 0 the next day. Chrome accepts it as a manifest version. Bump `apps/extension/package.json` whenever extension or capture code changes; CI's `check:extension-version` enforces it.
- Web UI uses the shadcn components (Base UI), theme, and fonts in `packages/ui`; add a missing component there with the shadcn CLI (see its README) rather than writing one.
- The extension keeps its own copies of the shadcn components it uses and a trimmed theme (`apps/extension/src/ui`) for now. Copy a shadcn component in when the extension needs one, rather than writing one, and change shared colours and fonts in both.
- Fetch and change data in the web app with TanStack Query (`useQuery`, `useMutation`), not `useEffect` with `fetch` or hand-managed loading and error state. Its queries live in `packages/web/src/lib/api.ts`.
- Add or change a product route only in the route manifest (`packages/web/src/route-manifest.ts`), then run `bun run generate-routes`; never edit a generated route file. Next.js reads segment config (`runtime`, `dynamic`, `maxDuration`) only as literals in the route file itself, and a re-exported `maxDuration` silently falls back to the platform default, so the generator writes them out and CI's `generate-routes --check` fails when a file differs. It reads a proxy's `config.matcher` only as a literal too, so each app's `proxy.ts` copies `productMatcher` (`packages/web/src/proxy.ts`) by hand, and its `proxy.test.ts` fails when the copy misses a path: update both when a page's address changes.
- Put every signed-in page under `/app`, in its sidebar layout, and keep the root for sign-in and consent. When a page's address changes, redirect the old one in `moved` (`packages/web/src/proxy.ts`), since installed extensions and connected agents link to it.
- The product reaches a deployment's own layers (metering, limits, operator admin and other Better Auth plugins, a provider account) only through `ServerHooks` (`packages/server/src/hooks.ts`) and the UI deployment (`packages/web/src/deployment.tsx`), passed in as parameters by each app's `deployment/`. Never import a deployment's layers into a package, and keep the no-op defaults working: they are what `apps/web` runs.
- Lean on Better Auth: for anything auth-shaped (sign-in, sessions, OAuth, organizations, members, invitations, roles, API keys), use its plugins and Better Auth UI unless there is a clear reason not to, and say the reason in a comment where our code takes over. Organizations and memberships are app tables the auth adapter sees through its own Drizzle definitions, with Better Auth's `id` as the row's `public_id`, so app columns and integer keys stay out of its reach.
- Shape every table and migration by the data conventions: an integer `id` primary key, and a TypeID `public_id` only for rows referenced outside the server; `timestamps()` (`created_at`, and `updated_at` where rows change), with lifecycle as nullable `*_at` columns rather than booleans; states as `text` with a CHECK constraint built from one `as const` list, not Postgres enums; an index on every foreign key column; and app data in app tables keyed by `membership_id` (a person in one organization), or by `user_id` only for what belongs to the person in every organization, never on Better Auth's tables. `bun run db:generate --name <change>` writes the migration. It must work with the code already deployed, so destructive changes expand in one release and contract in a later one, and an applied migration is never edited.
- Give every API route and server service an integration test (Vitest, in process, with PGlite and real Better Auth) covering session, origin, validation, status codes, ownership, and failure paths, in the same change that adds or changes it. Migrate one PGlite template per file in `beforeAll` and give each test `await template.clone()`; never migrate a new database per test. Use unit tests only for dense pure logic, and don't write tests that restate configuration or constants, snapshot output, or check display-only UI.
- Keep timings for computers, computer sessions, and MCP tool calls in `packages/server/src/computer-timing.ts`, and the E2B adapter's own command timings in `packages/e2b/src/timing.ts`, which it imports from. Give each a comment saying what it bounds and how its value was chosen, and derive related values from each other instead of repeating numbers.
- Existing computers never get a new template. Put a file computers need in `HELPERS` (`packages/e2b/src/index.ts`), and Chrome's flags in `ENSURE_CHROME`, so the refresh on `computer_open` delivers it to them. A change to installed packages or the OS reaches only new computers, and existing ones only by a reset, so say so in the commit.
